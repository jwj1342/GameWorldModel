# 进展与已知问题

最后更新 2026-09-19。

## 现在的状态

整条管线已经跑通。输入一段视频，感知、证据提取、程序生成、编译、渲染比对、修订、玩法绑定、自动试玩和报告全部自动完成，一条视频在 CPU 节点上大约五分钟。用了三段片段测试，两段是从 Wikimedia Commons 下载的真实视频，一段是用内核自己渲染的合成场景。

Plarail 玩具火车这段视频里，玩具火车被跟踪成两段沿轨迹运动的物体，地板和背景被当成静态结构。输送线这段视频是俯拍，地面平面用面向相机的主平面代替，皮带、金属臂和纸箱都被识别出来但都判成静止。合成片段的情况最好，用真值感知时升降平台被判成周期平移，门被判成绕轴转动，矿车被判成轨迹运动，四枚金币按实例分开。三段视频生成的游戏都能让自动试玩走到终点。

模型这一层现在走 OpenRouter，默认 GLM-4.6V，一条视频六次调用，费用一美分左右。合成片段上模型写出的程序分数是 0.55，直接从证据翻译是 0.71，说明模型目前还会把一些证据抄错或改坏。两段真实视频上两种方式分数差不多，都很低，因为几何体替身和真实画面没法在外观上比较。修订环节每次都会提出修改，但两轮下来分数基本不变。

## 一个影响所有历史分数的 bug

内核渲染时开了抗锯齿，而物体 ID 通道是把编号编码进像素颜色的，多重采样会在物体边缘把相邻编号混成不存在的颜色，Python 这边精确匹配就把这些像素整片丢掉了。实测一张 ID 图里注册表只有 4 项却出现 16 种颜色，越界像素 865 个，小物体周长占比大受害最重。掩码重叠在总分里占一半权重，所以下面表格里 2026-09-19 那批分数是被系统性压低的，尤其是"物体越小分数越低"这个结论里掺了渲染伪影。

现在无头模式关掉了抗锯齿，越界像素降到 0，`scripts/check_id_pass.py` 把这个检查固化进了冒烟流程。同一份配置（真值感知加假模型）改动前是 0.245，改动后是 0.623。下面表格里的其它数字还没重测。

这是同一个坑的第二次：之前 three.js 默认输出 sRGB 也把编码通道做了 gamma 变换，当时让所有分数接近零。结论是编码通道不能经过任何后处理。

## 与设计文档不同的地方

设计里的 ViPE 换成了 VGGT，因为 ViPE 要编译 CUDA 扩展，第一次装没成功。VGGT 给出的是相对尺度，先按首帧相机离地 1.2 米定标，绑定的时候再把最大静态足迹缩放到 24 米的游戏尺度。SAM 3.1 需要申请权限，先用 Grounding DINO 加 SAM 2.1。物体轨迹用掩码质心加深度反投影，没有用点跟踪。可行走面直接取最大的静态顶面，没有用导航网格。编译器只做校验、素材解析和打包，内核直接解释程序，没有生成代码。素材只有几何体替身。玩法模板只有第三人称平台跳跃。程序合成模型从设计里的自托管 Qwen3.5-27B 换成了 OpenRouter 上的 GLM-4.6V，自托管方案的脚本和配置还保留着。

## 已知问题

模型写出的程序在合成片段上曾经低于直译（0.55 对 0.71），原因查清了：内核把 periodic 运动的 `pose.pos` 当作振荡中心，而提示词里没写这条，反而让模型对齐首帧位置，整条轨迹会偏掉最多一个振幅。现在提示词和 DSL 文档都补了这条语义，生成之后还会按观测中心强制重心化。

运动分类基于掩码可见表面的质心，相机一动静止物体的质心也会漂，所以静止的东西容易被判成移动，小物体的原地旋转也常被判成静止。现在靠尺寸相对阈值、运动一致性、和相机运动的相关性以及静态类别先验来缓解，根本的解法是按设计用三维点轨迹做刚体运动估计。VGGT 对运动物体的深度不可靠，所以动态物体的三维位置有系统误差。地面上的小物体用掩码最低点和地面的交点来定位，比深度稳，但只在物体确实贴地的时候启用。自动试玩只会直线走向目标，受阻就跳或者侧步，目标默认放在地面最远的角上，高台上的目标走不到。模型返回的 JSON 偶尔漏逗号或者不按 schema，客户端做了修复和重试。

## 环境上踩过的坑

集群 wheelhouse 里的 vllm 0.25 钉的是 torch 2.11，和感知用的 torch 2.14 冲突，所以分成两个 venv。flash_attn 的 wheel 绑定 torch 2.9，装了它会把 torch 拉回去，感知环境不装它。计算节点经代理能访问 GitHub、HuggingFace、OpenRouter 和各家 API，但访问不了 npm registry、Playwright 的浏览器下载和 HuggingFace 的 cdn 大文件，所以 Node 依赖在登录节点打包，VGGT 权重在登录节点下载。three.js 默认输出 sRGB，ID 和深度通道的编码字节会被 gamma 变换，渲染这两个通道时要切到线性输出，这个问题曾让所有比对分数都接近零。自托管 vLLM 在 L40S 上要加载 cuda 模块给 flashinfer 编译，还要把并发数压到很低才不会 OOM，最后因为 GPU 排队太久改用了 OpenRouter。

## 还没定的事

1. 关键帧数（8 或 16）与每帧分辨率，决定单次调用的视觉 token 预算；见 `design-notes.md` 模型一节的成本估算。
2. 程序生成第二轮起输出 JSON Patch 还是完整 JSON；需在阶段三验证 VLM 写 Patch 的可靠性。
3. 视频中已有玩家角色（第三人称游戏录屏）时，是否把该角色从物体集合中剔除，由模板重新生成。
4. 游戏内相机与视频相机的关系：默认游戏相机由模板控制，视频相机轨迹只用于回放模式与重渲染比对。
5. 测试片段的许可：Godot 示例项目为 MIT，Kubric 数据许可待确认。
