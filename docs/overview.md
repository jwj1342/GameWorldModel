# 项目总览

这份文档是整个项目的入口。新加入的人先读这一篇，再去 GitHub issue 里按优先级看具体任务。

## 这个项目在做什么

给一段 10 秒到 1 分钟的普通视频（手机拍的、网上下的都行），自动产出一个能在浏览器里打开、能用键盘操作的 3D 场景，并且这个场景里的东西会按视频里的方式运动。

整条流程是这样：

```
视频
 └─ 感知：抽关键帧，估计相机位姿和深度，分割出物体并跨帧跟踪，
    拟合每个物体的运动规律  ──────────────────────►  证据（evidence.json）
                                                        │
 ┌──────────────────────────────────────────────────────┘
 │
 └─ 生成：把关键帧和证据摘要喂给视觉语言模型，分三阶段写出场景程序
    （先相机和静态结构，再物体几何和初始位姿，最后运动和事件）
                                                        │
                                                   program.json
                                                        │
 └─ 编译：schema 校验 → 语义校验 → 打包成一个 game/ 目录
                                                        │
 └─ 运行：浏览器里的固定运行时读取 program.json 把世界跑起来
                                                        │
 └─ 反馈：无头浏览器渲染三个通道（画面、深度、物体编号），
    和原视频逐帧比对打分，分数低的地方回头让模型改  ──┘（最多三轮）
                                                        │
 └─ 绑定与试玩：推断出生点、目标、收集物、危险物，自动试玩一遍，出报告
```

## 关键术语

读 issue 之前先对一下这几个词的意思。

**场景程序（program.json）** 是整个项目的核心产物，一份 JSON，描述场景里有哪些静态结构、哪些物体、每个物体长什么样、怎么运动、什么条件触发什么事件。它是我们说的「4D 场景程序」。

**DSL** 指这份 JSON 的格式规范，也就是我们自己定义的那套描述语言，由一个 JSON schema 约束。目前支持七种运动类型：静止、沿路径运动、绕轴转动、沿轴滑动、周期平移、周期转动、自转。目前还表达不了自由刚体运动（抛物线、碰撞弹开）和父子关节链，这是已知缺口。

**内核（kernel）** 指浏览器里那个固定的运行时代码。它是写死的，模型不生成代码，只生成数据（也就是 program.json），内核负责解释这份数据把世界跑起来。这个「固定内核、生成数据」的分工是整个设计的基础。

**证据（evidence）** 指感知模块的输出，包括每个物体的包围盒序列、运动类型猜测、接触关系、地面平面等等。它是喂给模型的输入之一。

**三个渲染通道**：画面通道就是正常的彩色图；深度通道把距离编码进像素；物体编号通道给每个物体涂一个唯一的纯色，用来做逐物体的掩码比对。后两个通道的像素值是编码数据，所以渲染时不能经过任何色彩后处理，这个坑踩过两次。

**感知的三档配置**。跑实验时经常需要切换证据从哪来：**真值感知**指直接用已知的正确答案当证据，只在合成数据上可用，用来排除感知误差看上界；**神经感知**指跑真实的感知模型（VGGT 估位姿深度、Grounding DINO 加 SAM 做分割），真实视频只能用这一档；**假模型**指用一个不调用任何模型的桩来代替视觉语言模型，用来在不花钱不占 GPU 的情况下测通管线。

**分数**。现在 issue 里出现的 0.245、0.547、0.623、0.714 这类数字，是渲染结果和视频逐物体比对得到的一个综合分，范围 0 到 1，越大越好。重要提醒：**这个分数只在同一段视频、同一档配置内部可比**，跨视频或跨配置比较没有意义。而且这套打分方式本身有结构性缺陷（见 #4），正在被替换，所以现有的历史数字都只能当参考。

## 代码大致长什么样

```
gwm/            Python 管线
  perception/   感知：抽帧、位姿深度、分割跟踪、证据提取
  synthesis/    生成：调模型写程序、反馈循环
  compiler/     编译：schema、校验、打包
  feedback/     渲染比对与打分
  binding/      玩法绑定
  playtest/     自动试玩
kernel/         浏览器运行时（固定代码，不由模型生成）
harness/        Node 加 Playwright，负责无头渲染和自动试玩
configs/        所有配置，包括消融开关
prompts/        提示词，每个角色一个文件
docs/           设计文档
```

## 关于 RP.md

仓库里有一份 `RP.md`，是项目最早的研究提案，写于开工之前。它里面有很多内容仍然有效（相关工作调研、技术选型理由、一些实验设计的想法），所以 issue 里会引用它。

但要注意：**凡是 RP.md 和这些 issue 冲突的地方，以 issue 为准。** 典型的冲突包括数据规模（RP.md 写的 10 万条是设想，实际规模见 #5）、技术选型（部分方案因为装不上或排不到 GPU 换掉了）、以及贡献清单（以 #10 为准）。

把 RP.md 当成背景资料读，别当成现行计划。

## 从哪开始读

代码怎么跑见 `RUNNING.md`，怎么参与见 `CONTRIBUTING.md`，设计细节见 `docs/architecture.md` 和 `docs/design-notes.md`，当前进展和已知问题见 `docs/status.md`。

研究计划和任务分工在 GitHub issue 里。先看标了「论文」前缀的那个，它是核心主张和贡献清单，决定了其它工作为什么要做；再看标了「规划」前缀的，那里有时间线、算力预算和决策点。然后按优先级标签看具体任务。

## 遇到看不懂的地方

这份文档和那套 issue 的目标，是让没读过代码的人也能看懂。如果你发现某处跳跃、某个术语没解释、或者必须翻代码才能理解，那是我们的问题，开个 issue 说一声，我们补。
