# 相关工作补充：用编码智能体生成显式场景程序

`related-work.md` 的调研停在 2026-09-18。而 GPT-6 Astra 在 2026-09-03 发布之后，
九月和十月出现了一批「让编码智能体写出显式场景程序」的工作，其中至少一篇已进
NeurIPS 2026。这一篇把那一批整理出来，回答三个问题：我们的基础方法是不是走错了、
别人做到什么程度、哪些做法我们该直接拿过来。

结论先说：**方法方向没有走错，这是当前一条热门且已被顶会认可的路线。但我们在三处
具体做法上落后，而且其中两处正是我们现在卡住的地方。**

## 这一批是什么

| 工作 | 输入 | 产出 | 关键做法 |
|---|---|---|---|
| LEGO-Anything（arXiv 2609.36380，09）| 单图 | Blender 代码 | 智能体闭环：写码 → 执行 → 看渲染 → 改 |
| NeoWorld-Pro（arXiv 2608.24212，**NeurIPS 2026**）| 单图 | Blender Python → URDF + USD | **物理在环**：Isaac Sim 里跑，不合理就修 |
| NeoWorld-3（arXiv 2610.27690，10）| 单图 | 代码定义的物理世界 | — |
| Agentic Real2Sim（arXiv 2607.19190）| 视频（DROID 机器人）| MuJoCo episode | 偏机器人数据 |
| Agentic RSR（arXiv 2610.10479，10）| 工作区视频 + 机器人模型 | MuJoCo | 用已知机器人尺寸定米制尺度 |
| LiteReality-Agent | RGB-D | 可 articulate、simulation-ready 室内场景 | 把重建当软件工程做 |
| BVB（arXiv 2609.15478）| 视频 | Blender 程序 | 是个基准，不是方法 |

更早的前身：SceneCraft（2024，LLM 写 Blender 代码）、VIGA（arXiv 2601.11109）、
Thinking in Blender（arXiv 2606.02580）、Code-as-room（arXiv 2605.18451）。

## 对 `related-work.md` 里「定位」那一节的影响

原来的说法是「现有工作四支各占一角，没有系统走通单目视频 → 带时序与动力学的场景
程序 → Web 引擎」，并把「4D（动态）」和「程序化表示」两环同时缺失作为本课题的位置。

**这个定位基本还成立，但缝隙比九月窄了：**

- NeoWorld-Pro 已经做到「单图 → 程序 → 关节 + 物理属性 → 仿真器里验证」。
  **程序化表示这一环不再是空白**，缺的只是视频输入和时序动力学。
- Agentic Real2Sim 和 Agentic RSR 确实吃视频，但**都绑在机器人数据上**
  （DROID episode、工作区视频 + 已知机器人模型），不是任意视频。
- 没有一篇同时做到「任意单目视频 + 观测到的运动 + 可交互程序」。

所以我们的位置仍在，但**写作时不能再说「没人做程序化场景表征」**，必须说清楚我们
和 NeoWorld-Pro 的差别在输入模态和时序建模上。

## 五条可以直接拿过来的做法

### 一、配对容差应该是相对的，不是绝对的

LEGO-Bench 的几何分 `R` 是 F@5%：把可见表面投到图像平面，按实例掩码分到物体上，
逐物体算精确率和召回，**容差是 `τ(g) = 0.05·z(g)`，随深度缩放**。

我们的 `scripts/eval --max-dist` 是**绝对米制**（当前 0.45 米）。这件事我们自己
踩过——绝对阈值不是尺度不变的，在小场景里等于「什么都能配上」，在大场景里又过紧。
LEGO-Bench 用相对容差是对的，**这一条值得直接改**。

注意一个差别：他们**不做规范对齐**（"compared in camera coordinates without
alignment"），而我们做偏航 + 水平平移对齐。两种口径不能混着比。

### 二、关节不要靠几何推断

这是最要紧的一条。NeoWorld-Pro **根本没有单独的关节检测方法**——由 MLLM 从图像
语义直接生成关节程序（论文举的例子是「从看得见的把手推断抽屉的内腔」），然后
**用物理去修**。

他们的关节指标：

| | NeoWorld-Pro | 最强基线 Articraft |
|---|---|---|
| 漏检率 | **11.83%** | 22.45% |
| 类型错误 | **18.78** | 29.39 |
| 轴误差 | 28.52 | 30.14 |
| 支点误差 | 0.19 | 0.23 |

对照我们：关节那一档在神经感知下 **0/7 全错**，全真值几何 + 全真值分割下也只有
**1/13**。根因已经查清是 #7 的 ICP 伪造转动（静止物体被解出 26.6° 转动，而铰链
门槛是 8°），而那条线上已经排除了二十条修法。

**也就是说：我们在用一条已经证明走不通的几何路线，去做别人用语义先验 + 物理验证
做成的事。** 这是本次调研最值得行动的一条。

### 三、物理当验证器，不只当运行时

NeoWorld-Pro 的物理在环分两层：

- **物体级**：URDF 在 Isaac Sim 里跑自由落体和受力扰动，一个看视频的 MLLM 评审
  关键帧并提修改建议。**改动被限制在惯性参数、关节限位、阻尼、原点和碰撞几何**，
  不动运动学拓扑和可见几何。
- **场景级**：用 CEM 优化每个物体的四维扰动（平面平移、偏航、对数尺度），奖励
  = 语义 MLLM 分 + 穿模惩罚 + 漂移惩罚。

消融（表 4）：完整方法成功率 **92.85%**，去掉语义分 48.81%，**开环 44.05%**。
**闭环把成功率翻了一倍多。**

我们已经有 Rapier 在运行时跑物理，但只用来「跑」，没用来「验」和「修」。
这条的成本不高、收益有先例。

### 四、但不要盲目上智能体自评

LEGO-Anything 量了三个失败模式，其中两个对我们是警告：

- **迭代中回退**：GPT-5.6-sol 有 **29.6% 的编辑让分数变低**；最终提交比它自己
  最好的中间结果低 3.2 分。
- **自评不可靠**：让模型二选一判断哪个渲染更好，和指标方向的一致率——
  **几何上自评 45.8%（低于 50% 的随机水平）**，外观上 62.2%。跨模型评审
  45.4% / 63.9%。

**几何自评低于随机**，这是个硬结论。我们现在是单趟确定性翻译，天然没有这两个问题。
所以如果要引入智能体闭环，**必须带版本控制和外部判据**，不能让模型自己说好不好。
LEGO-Plugin 的三个模块正是针对这个：增强初始化（VGGT 恢复相机）、接地式精化
（SAM 3 + Depth Anything V2 做显式残差）、**版本控制（接受 / 修复 / 回滚）**。

### 五、外观要量，但不是和 3DGS 比

**这一批没有一篇拿 3DGS 或 NeRF 作对比。** NeoWorld-3 的开场白直接写
"Simulation-ready world reconstruction demands physical interactivity beyond
visual realism"。

但他们**确实量外观**：LEGO-Bench 的 `A` 是「用标准引擎重渲染，和参考图逐像素比，
最大通道误差 ≤ 30/255 的像素占比」。总分 `S = 均值( ½(R+A)·V )`，失败算 0。

一个有意思的对照：Gen3DSR 的室内几何分 **65.4%**（高于 GPT-6-astra 的 52.4%），
但外观分 **0.0%**，总分只有 30.1%。**几何和外观是可以分开赢的**，而我们目前的
处境接近 Gen3DSR——有一点几何，外观近乎没有（形状种类准确率 0.300，所有物体
渲成盒子）。

## 从生成的场景里读视觉任务（LEGO-World）

把生成出来的场景当成一个世界模型，从里面读检测、分割、深度：

| 任务 | 指标 | 从场景读出 | 专用模型 |
|---|---|---|---|
| 检测（COCO val2017）| Box AP ↑ | 30.14 | DINO 59.88 |
| 分割（LVIS v1 val）| Mask AP ↑ | 14.75 | SAM 3 53.96 |
| 深度（ETH3D）| AbsRel ↓ | 0.1554 | Depth Anything 3 0.0783 |

大约是专用模型的一半。作者的结论是「有希望但还不够精确」。

## 我们还站得住的差异化

1. **视频输入，而且用观测到的运动**。这一批主流是单图；做视频的都绑在机器人数据上。
   我们的 `motion` 字段和第一档（观测运动回放）在这批工作里没有对应物。
2. **样式与行为分写，而且在量**。没有检索到别人测解耦度。我们的行为漂移 0.207 米 /
   样式响应 0.247（见 #52）可能是新的。
3. **带真值程序的基准**。LEGO-Bench 是 simulator-grounded 的 208 张图；我们的数据
   由生成器产出、**有已知真值程序**，能算精确的逐物体配对指标，并且支持成对样本
   （同行为换样式）。这是我们手上独有的东西。

## 为什么在外观上比不过 3DGS，以及空白在哪

这一节不是文献摘录，是上面那批材料加上我们自己测量之后的分析，供写 motivation 用。

### 这是容量和结构的取舍，不是优化不够狠

| | 3DGS / NeRF | 场景程序 |
|---|---|---|
| 自由参数 | 约 10⁶–10⁷（每个高斯：位置、协方差、不透明度、球谐）| 约 10²–10³（N 个物体 × 位姿 / 形状 / 材质）|
| 优化目标 | **直接最小化与输入像素的光度误差** | 完全不碰像素 |
| 假设空间 | 任意斑点场，**包含**真实场景 | 资产库 + 基本体，**不包含**大多数真实物体 |
| 离散决策 | 没有 | 物体数、类别、基本体类型、关节类型，**全不可微** |

最根本的是第三行：**不是我们优化得不够狠，是真实场景根本不在我们的假设空间里。**
一个真实的笔记本不是盒子，资产库里也没有它。3DGS 不需要"认识"任何东西，
它只要把斑点摆到降低像素误差的地方。

第四行是第二重障碍：程序合成必须做离散选择，而这些选择不可微。
"检索哪个资产""这是铰链还是滑轨"都没法反向传播。

### 3DGS 正在从另一头走过来，撞上的墙正好是我们免费拥有的

有一条活跃的线在给高斯加物理：DecoupledGaussian（CVPR 2025）、PhysSplat
（ICCV 2025）、Scene-Level Heterogeneous Physics（arXiv 2606.21753）。
他们自己写的困难：

| 他们的难点 | 出处原话 | 我们这边 |
|---|---|---|
| 被遮挡 / 看不见的几何 | "no GS or NeRF method could restore objects **occluded by the scene** or missed due to object removal" | 直接给完整的几何体 |
| 物体能否真正脱离表面 | 早期方法里物体 "remain **constrained to the contacted surface**" | 从一开始就是独立刚体 |
| 从静态捕获推物理属性 | "extremely challenging task due to **limited supervisions**" | 表示里本来就有质量、摩擦这些槽位 |
| 抽网格 | "Gaussians are **unorganized**" | 不存在这个问题 |
| 接进物理引擎 | "physics engines **weren't designed for** Gaussian representations" | 本来就是为引擎生成的 |
| 只能回放不能外推 | "**Replay-based methods only play back** captured or generated motion, so they **can't simulate new dynamics**" | 正是核心主张里的"可外推" |

DecoupledGaussian 为了补一个物体的背面要用 Poisson 场填充加反复雕刻，
而且作者明说这套**牺牲纹理保几何**。

### 真正的不对称

> **外观对我们是容量问题，结构对他们是表示问题。**

容量问题可以买——更大的资产库、更深的组合、或者混合表示。
表示问题买不到：没法通过"优化得更狠"从一团斑点里长出"这是一扇门，它绕这根轴转"。

这是支撑本课题方向最硬的一条论据，而且它来自对方自己写的 limitation。

### 我们自己最大的困难

不是渲染不够真，是**假设空间不含内容，加上整条链路没有任何像素反馈**：

- 资产检索成功率 45%（118 个物体检到 53 个），而且当前基准真值全是基本体，
  **检索成功反而在形状种类上算错**
- 形状种类准确率 0.300，超过一半的物体渲成盒子
- **从感知到合成到编译，没有一处拿渲染结果和原视频比过**

第三条最要命，因为它可以修。

### 两个没人做的空白

**一、把光度一致性当损失，而不是当分数。** LEGO-Bench 的外观分 `A` 是"重渲染后
逐像素比"，但它只被当成评测指标。没有工作把它接成程序合成的**优化信号**
（渲染程序 → 和原帧比 → 改程序 → 再比）。LEGO-Plugin 的 grounded refinement
用 SAM 3 + Depth Anything 做显式残差，已经在摸这个边，但没有直接用像素。

**二、3DGS 与场景程序的结合整体是空白。** 检索下来没有任何工作把两者放在一起。
给高斯加物理的那一线，和让智能体写程序的那一线，目前互不引用。

### 一个我们自己没用上的容量来源

内核的 `kernel/scene.js` **已经支持 `kind: "composite"`**（带 `parts` 的组合体，
见第 104、115 行），但它只能通过类名正则的兜底分支触达（`tree|plant|bush`、
`train|car|cart|...`）。实测产出里 **70 个物体节点全部是 `asset`，一个组合体都没有**。

也就是说：**提升假设空间容量的机制已经在代码里，只是从来没被用过。**
用组合体加深结构，比引入非程序的残差更可取——因为组合体仍然是程序，
仍然可编辑、可仿真、可外推。

## 一个候选方向：把 3DGS 当教师，而不是当残差

这一节记的是 2026-10-23 讨论里成形的一个想法，以及围绕它查到的东西。
**它目前只是候选，没有实验。**

### 框架：蒸馏，不是残差

初版的想法是"程序管结构、高斯管外观残差"。那个版本有两个硬问题：

1. **分解不可辨识。** 残差分支足够强的话，盒子摆错位置高斯也能补回来，渲染照样
   好看——于是程序不再是场景的忠实结构描述，拖动物体时行为是错的，但你从渲染上
   看不出来。
2. **残差在新位姿下会塌。** 高斯只在观测到的视角上拟合过，物体一转到没见过的朝向
   （而那正是"可交互""可外推"的定义）残差就失效。这恰好把 3DGS+物理那条线已经撞上
   的墙（"can't simulate new dynamics"）引进我们的强项里。

改成**蒸馏**之后这两个问题都消失了：3DGS 是**教师**，程序是**学生**，
**最终产物只有程序**，高斯不进交付物。没有残差分支可以吸收结构误差，
也没有外观缓存会在新位姿下塌。

### 教师能给的，原始视频帧给不了

如果只是想要光度损失，直接拿视频帧比就行，不需要先拟合高斯。先拟合的价值在四点，
其中第一和第三是真正关键的：

1. **新视角监督。** 视频只覆盖相机实际走过的轨迹，而高斯能渲染相机从未到过的视角。
   这样就能监督程序**没被观测到的那些面**——而那正是我们的盒子最差的地方。
   原始帧给不了这个。
2. **稠密几何代理。** 在我们深度后端失败的地方也有一个表面估计。
3. **多视角一致的去噪目标。** 高斯在多帧上平均，抑制逐帧噪声。这一条对我们特别
   对症：实测逐帧包围盒中心的抖动是节点自身对角线的 **0.43–0.46 倍**，而且是
   **单调漂移**（见 #56），根因是"框跟的是可见表面，不是物体"。
   一个多视角一致的目标正是治这个的。
4. **可按物体分解的目标。** 配上掩码之后每个物体有自己的高斯集，可以逐物体拟合，
   而不是对着整帧算一个损失。

### 已知的坑，以及已知的解法

把结构化基元和高斯放在一起训练，有一个有文献记载的失效模式：

> Naively training 3D Gaussians and room layout meshes jointly can result in
> **ambiguity issues, leading to a single instance being represented by both
> primitives**. We address this issue by **using SAM masks as a guide**.
> ——《Integrating Meshes and 3D Gaussians for Indoor Scene Reconstruction with
> SAM Mask Guidance》（arXiv 2407.16173）

这正是上面第 1 条担心的实测版本。**而它的解法是用语义掩码做引导**——也就是说
"让物体去拟合语义遮罩"这个直觉，恰好是这个已知失效模式的已知对策。

同一篇还给了一条支持结构化表示的论据：

> A simple plane composed of a few colors can be effectively represented with a
> small number of meshes, whereas representing it with 3D Gaussians requires a
> **significantly larger number**.

高斯在平坦区域是浪费容量的。这说明两种表示**各有擅长的区域**，不是单纯的强弱关系。

### 它解决不了什么

**蒸馏改善的是拟合，不是表达力。** 如果真实物体是一台笔记本而我们的词汇表只有
"盒子"，更好的教师只会更精确地告诉你盒子有多不像笔记本——最好的盒子仍然是盒子。

所以这条路**必须和加深组合深度一起做**（见上一节：内核已支持 `composite`，
但我们一个都没产出过）。教师告诉你哪里错，组合体给你改正所需的词汇。
两者互补，不是替代。

### 为什么说它是空白

检索下来：

- 没有任何工作把 3DGS 蒸馏进**结构化场景程序**；
- Feature Splatting 做的是把视觉语言特征蒸馏**进**高斯（方向相反）；
- ShapeSplat 是 CAD → 高斯（流向相反）；
- 把光度一致性当**损失**而不是当分数，在编码智能体那一线也没人做
  （LEGO-Bench 的 `A` 只是评测指标）。

### 成本上的提醒

逐片段拟合 3DGS 本身是有成本的。按 #21 的实测，我们一趟 2000 条的重建已经约
40 GPU 小时，而账户的稳态额度约 12.6 张 L40S、近期已用到份额的 1.79 倍。
加一层高斯拟合之前要先算这笔账，或者只在子集上做教师。

### 一个不需要高斯的弱化版本

如果先不想引入高斯，这个想法有一个更轻的版本：**可微渲染**。把程序渲出来、
和原帧比、梯度回传到**连续参数**（位姿、尺寸、颜色），离散选择（几个物体、
哪个基本体、什么关节）仍然留给智能体搜索。

它拿不到"新视角监督"那一条，但其余三条收益都在，而且没有第二套表示要维护。
可以作为先走一步的版本。

## 再进一步：把"元素库"学出来

2026-10-23 讨论里的第三个想法：不要手写资产库，也不要固定的几个基本体，
而是**从一个训练集里把可组合的"元素库"学出来**。

这个想法有成熟的谱系，而且其中一篇的标题几乎就是它本身。

### 谱系

| 工作 | 做什么 | 对我们的意义 |
|---|---|---|
| **DreamCoder**（2020）| wake–sleep 的库学习：从已解的程序里挖抽象，用"程序似然 vs 库复杂度"的权衡来取舍 | 原型，但见下面的警告 |
| **ShapeMOD**（arXiv 2104.06392）| 3D 形状程序的宏操作发现 | 指出更早的文法归纳只能处理上下文无关语言 |
| **ShapeCoder**（arXiv 2305.05661）| 标题即"**从无结构基元中发现视觉程序的抽象**"，压缩目标，能处理复杂参数化重写 | **最接近这个想法的工作** |
| **ShapeLib**（arXiv 2502.08884）| 用大模型来设计这个库 | 它称 ShapeCoder 是 3D 库学习目前最好的方法 |

### 三条必须先知道的警告

**一、DreamCoder 在 3D 上是失败的。** ShapeCoder 作者在补充材料里写：

> When we attempted to run DreamCoder over PartNet data we observed it
> **did not find any solutions**.

他们给的原因是 DreamCoder 没有机制处理连续参数之间的关系，而那对视觉程序至关重要。
所以"照搬 DreamCoder"这条路有人试过并且失败了。

**二、ShapeCoder 的产物对大模型不友好。** 作者自己写：

> We experiment with how well LLMs can interact with ShapeCoder programs, and
> find that this is **challenging for frontier models**. ShapeCoder functions and
> parameters **do not have semantic-aligned names**, and tend to **over-focus on
> local patterns, especially when discovered from small seed sets**.

这对我们是直接的问题：我们整条链路（以及整个编码智能体那一波）都依赖模型去读写
这个词汇表。学出来一个模型读不懂的库，等于没学。ShapeLib 用大模型参与设计正是
为了解决这一点。

**三、小种子集会让抽象偏向局部模式。** 我们现在的批次是 12 条片段。
库学习要的是语料规模，这个量级远远不够。

### 训练集从哪来——这是最大的风险

如果从**我们自己生成器产出的真值程序**里学库，学到的就是生成器的词汇表。
那是循环的：我们会得到一个在自己的合成基准上完美、在真实视频上无用的库。
**这个风险必须在设计实验之前就想清楚。**

一个更有意思的版本是和上一节接起来：

> ShapeCoder 的输入是"**无结构基元**"。而逐物体分解之后的高斯，正是一堆无结构基元。

也就是说：**用 3DGS 当教师产出无结构基元 → 在语料上做压缩式抽象发现 → 得到元素库**。
这条不需要真值程序，监督来自真实视频本身，绕开了上面那个循环。
检索下来没有人这么做过。

### 还有一块完全空白：行为的词汇表

上面所有工作学的都是**几何**抽象。没有人学过**行为**的词汇表——
哪些运动模式反复出现、哪些关节类型可以组合、哪些交互可以复用。

而我们的表示里 `motion` 和 `interaction` 和几何是并列的。
**如果"元素库"要学，行为那一半比几何那一半更没人做过，也更贴近本课题的主张。**

### 时间上的判断

这是一个**独立研究课题的体量**，不是一个修补。DreamCoder 到 ShapeCoder 到 ShapeLib
是五年三篇。按 #21 记的投稿时间（CVPR 2027，11-16 截止），
**这条不属于这一轮**。记在这里是为了不丢掉，以及在写 future work 时有据可依。
