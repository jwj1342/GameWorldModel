# 第一阶段 Baseline 计划：从一段视频到一款可玩游戏

> 目标是尽快跑通"视频进、游戏出"的闭环，而不是把每个模块做到最好。计划按六个阶段组织，每个阶段用它交付的东西命名，以一个可以运行的 demo 收尾。不给阶段和产物编版本号。技术选型的依据见各层文档，架构与接口见 `architecture.md`。

## 1. 目标与范围

**输入**：一段 5~15 秒、无标定的单目 RGB 视频；可选一句话玩法提示，默认"第三人称平台跳跃"。

**输出**：`out/<clip_id>/` 目录，含 `evidence.json`、`program.json`、可直接用浏览器打开的 `game/`、每轮反馈记录与试玩记录（布局见 `architecture.md` 第 4 节）。

**跑通的定义**（内部验收，不是 benchmark）：

1. 十条测试片段中至少七条端到端产出可打开的 `game/`。
2. 经两轮反馈后，关键帧的逐物体 mask IoU 与 DINOv3 相似度相对第一轮有提升。
3. 产出的游戏能用键盘从出生点到达目标体，轨迹回放录像经 VLM 评审判定可玩。
4. 修改 `program.json` 里一个物体的运动参数后重新编译，渲染结果随之改变。

**明确不做**：模型训练；benchmark 与基线对比；六种玩法模板全做（先一种，第二种可选）；Gaussian 残差层（接口预留）。

## 2. 测试片段

| 来源 | 数量 | 特点 | 真值 |
|---|---|---|---|
| Kubric MOVi-E/F 合成片段 | 3 | 相机线性运动，1~3 个抛掷刚体，24 帧 | 逐帧相机、物体位姿与速度、实例分割、深度 |
| Godot 示例项目录屏（平台跳跃、俯视） | 3 | 真实游戏画面，含移动平台、可拾取物，需自行录制并导出引擎状态 | 物体位姿与运动参数 |
| 开源 three.js 游戏录屏 | 2 | 与目标运行时同构，含门、平台等 | 可从源码读出运动参数 |
| 手持视频 | 2 | 室内推门、桌上滑动物体等 | 无，仅定性 |

第一个阶段只需要一份手写的场景程序，不需要视频；第二个阶段起用上述片段的前三条，第五个阶段用全部十条。

## 3. 六个阶段

### 阶段一：手写程序跑通

**目标**：不接视频，用一份手写的场景程序验证内核、编译器与无头渲染 harness 三件基础设施。

任务：

- [ ] 固定内核：three.js + Rapier + recast-navigation + miniplex，systems 按优先级区间执行；实现 `window.__game` 的六个方法（见 `architecture.md` 5.3）。
- [ ] 平台跳跃模板：出生点、目标体、可行走面、收集物、危险物五个槽位；Rapier KinematicCharacterController 控制角色；第三人称跟随相机。
- [ ] 编译器：JSON Schema 校验 → 语义校验 → 生成 `scene.js` / `motions.js` / `events.js` / `binding.js` → 写 `index.html`；错误输出为结构化列表。
- [ ] 运动节点编译：static、trajectory、revolute、prismatic、periodic_translate、periodic_rotate、spin 七种各一个纯函数 `pose(t)`。
- [ ] 无头 harness：Playwright 加载 `game/`，按关键帧时刻调用 `render` 输出 rgb / depth / id 三张 PNG；`step` 驱动固定步长；Slurm 作业脚本按 `cluster.md` 的约定解包依赖。
- [ ] 手写一份场景程序：地面、两面墙、一个周期升降平台、一扇定时开门、三枚旋转金币、出生点与目标体。

交付物：`kernel/`、`compiler/`、`harness/`、`examples/handwritten/program.json` 及其 `game/`。

验收：手写程序编译成功；无头渲染 30 帧用时小于 10 秒；本地浏览器打开后键盘可控角色到达目标；三张 pass 图内容正确（ID 图每个物体一种平色，深度图近亮远暗）。

风险：Rapier 与 recast 的 WASM 在免打包 ESM 下的加载路径；Chromium 在集群上的启动参数。后者已实测通过。

### 阶段二：视频变证据

**目标**：对三条片段跑通感知栈并产出 `evidence.json`。

任务：

- [ ] 感知环境：`python/3.11.5` 虚拟环境，装 ViPE、SAM 3.1、SpatialTrackerV2、DINOv3、DreamSim；权重预下载到 `/project`。
- [ ] ViPE：内参、位姿、近度量深度、动态掩码；对 Kubric 片段与真值比对 ATE，确认尺度可用。
- [ ] SAM 3.1：用 VLM 对首帧列出的名词短语做概念分割，得到实例掩码序列与跨帧 ID。
- [ ] 轨迹：每个实例掩码内取点跑 SpatialTrackerV2，得到 3D 轨迹与动静标签。
- [ ] 证据提取：掩码 × 深度反投影 → 去离群 → 地面法向对齐后 PCA 得逐帧 OBB → SE(3) 平滑 → 螺旋拟合分类运动类型 → 接触关系 → 静态平面候选。
- [ ] 可视化：把 OBB 序列与运动类型叠加到视频帧上输出 mp4，用于目测。

交付物：`perception/` 脚本、感知作业模板、三条片段的 `evidence.json` 与叠加视频。

验收：`evidence.json` 通过 schema；叠加视频上 OBB 与物体贴合；Kubric 片段的运动类型分类与真值一致，位姿 ATE 在合理范围。

风险：真实手持视频上 ViPE 尺度漂移；SAM 3.1 在小物体上的跟踪丢失。备选见第 5 节。

### 阶段三：证据变静态程序

**目标**：VLM 根据关键帧与证据写出相机与静态结构、物体几何与初始位姿，并经两轮渲染反馈修订。

任务：

- [ ] 程序生成 agent：Pydantic AI，模型可在 `claude-opus-5` 与 vLLM 上的 Qwen3-VL 之间切换；输入 8~16 张关键帧、`evidence.json`、DSL schema、few-shot；输出完整 `program.json`。
- [ ] 分阶段提示：先相机与静态结构，再物体几何与位姿；每阶段先过校验，编译错误直接回喂。
- [ ] 数值反馈层：逐物体 mask IoU、质心偏差、SILog 深度误差、DINOv3 余弦、DreamSim；生成逐物体 pass/fail 子句。
- [ ] VLM 批评：只接收失败子句对应的裁剪对与差异叠加图，输出结构化 JSON。
- [ ] 修订：第二轮起 VLM 输出 JSON Patch，每轮 2~4 个候选，按数值分与 VLM 成对比较选优，允许回退。
- [ ] 素材解析暂用 primitive 兜底（按 extent 生成 box / cylinder 组合）。

交付物：`agent/` 循环代码、提示词、三条片段的 `rounds/` 记录与 `report.md`。

验收：三条片段第二轮的 mask IoU 与 DINOv3 均高于第一轮；相机重投影误差下降。

风险：VLM 在 JSON Patch 上的可靠性；关键帧数与 token 预算。前者若不稳则退回每轮输出完整 JSON。

### 阶段四：让物体动起来

**目标**：加入运动程序阶段，动态物体在回放模式下跟随视频中的运动。

任务：

- [ ] 第三阶段提示：每个动态物体的 `motion` 与 `events`，以证据中的 `motion_guess` 为先验，VLM 可否决。
- [ ] 轨迹反馈：程序轨迹与观测 OBB 轨迹的质心 ATE、周期与幅度相对误差，纳入子句。
- [ ] 时序一致性检查：物体在程序中的出现区间与观测区间的重叠。
- [ ] 可编辑性演示：改一个周期参数重编译，输出前后对比视频。

交付物：三条片段的运动程序与对比视频。

验收：动态物体 ATE 相对第一轮下降；Kubric 片段的运动类型与真值一致；改参数后渲染随之变化。

风险：VLM 写不好运动参数。备选是把拟合结果直接编译进程序，VLM 只负责类别、几何与事件。

### 阶段五：程序变游戏

**目标**：绑定玩法模板，十条片段端到端产出可玩游戏，并有自动试玩验收。

任务：

- [ ] 绑定规则：recast 对静态结构与静止物体生成 navmesh；出生点取距首帧相机最近的可站立点；目标体取最远连通点或提示指定物体；金币、宝石、钥匙类进收集物；岩浆、尖刺、水类进危险物；运动物体保持其运动作为动态平台。
- [ ] 玩家角色：KayKit CC0 角色与动画，Rapier KCC。
- [ ] 试玩回放：由 navmesh 路径生成按键序列，`__game.input` 逐帧注入，录 2 fps 帧与 `state()`；规则判定到达、卡死、帧率；VLM 评审可玩性与视觉一致性。
- [ ] 端到端脚本：一条命令从视频到 `out/<clip_id>/`，作业内完成。
- [ ] 十条片段全部跑一遍，整理失败原因。

交付物：`binding/`、`playtest/`、端到端脚本、十条片段的结果与失败分析。

验收：十条中至少七条产出可玩游戏并通关；失败案例有归因。

风险：手持视频的静态结构不成"关卡"。备选是绑定时允许模板补充地面与边界。

### 阶段六：素材与展示

**目标**：把 primitive 兜底换成小型素材库检索，补齐第二模板与展示材料。

任务：

- [ ] 素材库：登录节点抓取 Kenney、KayKit、Quaternius 的 CC0 GLB 约 1,500 个，归一化后存 `/project`；计算节点渲染四视图缩略图，CLIP 嵌入入 FAISS。
- [ ] 检索：裁剪图 + 类别文本融合排序，VLM 重排（尺寸先验、是否 rigged）；低于阈值回退 primitive。
- [ ] primitive 配方库：门、矿车、平台、金币、树等参数化生成器，配方格式沿用 threejs-scene-factory 的 `catalog.json` 思路。
- [ ] 可选：TRELLIS.2-4B 对每条片段 1~3 个 hero 物体生成。
- [ ] 可选：第二模板 `topdown_survival`（俯视、yuka 巡逻敌人）；Spark 残差层接口。
- [ ] 展示：demo 页面与视频；技术报告草稿。

交付物：`assets/` 库与检索服务、demo、报告。

验收：检索命中率人工抽查；demo 视频。

## 4. 阶段依赖

```
阶段一 ──► 阶段三 ──► 阶段四 ──► 阶段五 ──► 阶段六
阶段二 ──┘
```

阶段一与阶段二相互独立，可以并行。阶段六的每一项都可选，前五个阶段已经构成闭环。预计每阶段一周，六周完成；之后三周留给 benchmark、消融与写作（RP 第 4、5 节）。

## 5. 备选方案

| 风险 | 备选 |
|---|---|
| 感知在真实视频上不稳 | 定量只做合成片段与开源引擎录屏；真实手持视频只做定性 |
| VLM 写不好运动程序 | 运动参数由证据提取的螺旋拟合直接编译进程序，VLM 只负责类别、几何、事件与绑定；程序表征不变，只是参数来源变化 |
| API 成本或配额 | 切 Qwen3-VL-32B-Instruct FP8 自托管（2×L40S）；Vulcan 的 Aleph 推理服务也可用 |
| 无头 GPU 渲染出问题 | SwiftShader CPU 路径已实测可用 |
| 素材检索质量差 | primitive 配方保证可执行；视觉质量交给残差层 |
| 六周做不完阶段六 | 前五个阶段已是"视频进、游戏出"的闭环，阶段六全部可选 |

## 6. 待决事项

1. 关键帧数（8 或 16）与每帧分辨率，决定单次调用的视觉 token 预算；见 `models.md` 的成本估算。
2. 程序生成第二轮起输出 JSON Patch 还是完整 JSON；需在阶段三验证 VLM 写 Patch 的可靠性。
3. 视频中已有玩家角色（第三人称游戏录屏）时，是否把该角色从物体集合中剔除，由模板重新生成。
4. 游戏内相机与视频相机的关系：默认游戏相机由模板控制，视频相机轨迹只用于回放模式与重渲染比对。
5. 测试片段的许可：Godot 示例项目为 MIT，Kubric 数据许可待确认。
